# ADR-0009: ProxyJump, SOCKS5/HTTP proxy and keyboard-interactive

- Status: accepted
- Date: 2026-09-27

## Context

4.4 asks for three ways of reaching a server that a direct TCP connection cannot: through an SSH jump host (`ssh -J`), through a SOCKS5 or HTTP proxy, and with keyboard-interactive authentication for SSH servers that only offer it. All three sit below the protocol adapters (`adapters/remotefs/sftpfs`, `adapters/remotefs/ftpfs`), which already take a `DialContext` for the raw TCP step and a `VerifyHostKey` for the handshake; `adapters/remotefs/connect.Connector` is the one place that builds both from a `site.Site` and the network guard's own dialer (`netguard.Policy.Dialer`). This ADR decides what a site's proxy and jump settings look like, where their credentials live, how the network guard still applies once traffic no longer goes straight from this server to the target, and whether keyboard-interactive needs new code at all.

## Decision

**Keyboard-interactive needs no new code.** `sftpfs.authMethods` already offers `ssh.KeyboardInteractive`, answering every prompt with the site's stored password, alongside plain `ssh.Password`, whenever a password is configured (`sftpfs.go`, `authMethods`). A server that refuses `password` outright and only offers `keyboard-interactive` — common on hardened SSH servers — already authenticates today. This is the same trade-off FileZilla and every other non-interactive SFTP client makes: a prompt that is not literally "Password:" (a numeric TOTP code, say) cannot be answered without asking the person live, which this server-side connection has no channel to do mid-handshake; that case is out of scope, same as for any batch SSH client, and is written down here so it is not mistaken for an oversight.

**Proxy (SOCKS5 or HTTP CONNECT), on any protocol.** A site gains an optional `Proxy`: `Type` (`socks5` or `http`), `Host`, `Port`, and an optional `Username`/`Password`. It replaces the raw TCP dial the network guard's own dialer performs, for SFTP, FTP and FTPS alike, since proxying only changes how the *first* TCP connection is made — everything above it (TLS, SSH handshake, authentication) is unaffected. A new package, `adapters/proxydial`, builds a `DialContext` that: dials the proxy address (through the network guard's own dialer, so the proxy's *own* address is checked exactly like a site's host is today), then either runs the SOCKS5 client handshake (`golang.org/x/net/proxy`, whose SOCKS5 dialer implements `proxy.ContextDialer`) or writes an HTTP `CONNECT host:port` request with an optional `Proxy-Authorization: Basic` header and reads the response status line, refusing anything but `200`. The proxy's password is a new secret kind (`SecretProxyPassword`), sealed and opened exactly like a site's password.

**ProxyJump, SFTP only, one hop.** A site gains an optional `Jump`: `Host`, `Port`, `Username`, `AuthMethod` (`password` or `key`), with its own `SecretJumpPassword`, `SecretJumpPrivateKey` and `SecretJumpPassphrase`. When set, `connect.Connector` first dials and fully authenticates an SSH client to the jump host — through the site's proxy too, if one is also set, and through the network guard's dialer either way, so the jump host's address is checked like any other site host — then asks that client to open a `direct-tcpip` channel to the real target's `host:port` (`ssh.Client.DialContext`, the same call `golang.org/x/crypto/ssh` uses for local port forwarding) and hands that channel to `sftpfs.Dial` as its connection, exactly as if it were a raw TCP socket: the target's own host key check, key exchange and authentication happen over it unchanged. Chained jumps (`-J a,b,c`) are not supported; one jump host covers what people actually configure in FileZilla's own "Generic proxy" dialog, and a second hop can be added later without changing this shape if it turns out to matter. A jump host is meaningless for FTP/FTPS, which have no equivalent of an SSH channel to tunnel through, so `Jump` is refused (a validation error) on anything but an SFTP site.

**The network guard still runs on every hop it can see.** The proxy's host and the jump host's host are both literal addresses configured by the person, exactly like a site's own host, so `netguard.Policy.CheckHost` refuses a private, loopback, metadata or reserved one for either, by default, the same way it already refuses one for a site — an administrator who has widened the allowed private ranges (3.7) widens it for these too, since it is the same check. The *final* target's host, when reached through a jump, gets the same static check on the string the person configured, but once the connection leaves through the jump host's own network stack, this server cannot see what the jump host actually resolves that name to — the residual risk any `ProxyJump` or corporate bastion setup carries, not something this feature can close from the outside. It is bounded by the jump host itself already having passed the guard: reaching an internal address is only possible by first being trusted to reach a host allowed to reach it, the same trust chain an actual bastion host is built on. This is written up in `docs/security/fase-4.md` at the end of the phase.

**Vault storage.** The four new secret kinds (`SecretJumpPassword`, `SecretJumpPrivateKey`, `SecretJumpPassphrase`, `SecretProxyPassword`) are sealed and opened exactly like the three that exist today: scoped to the site's ID, under the DEK of the workspace that owns it, through the same `sealChanges`/`OpenSecret` machinery, with no new scoping concept. `SecretChanges` gains the matching four write-only fields (nil keeps, empty string removes, anything else replaces), so a jump host's or proxy's credential is never read back once written, like every other secret.

## Consequences

- Positive: no new transfer machinery, connection pool or scheduler changes — the jump and proxy only change how `connect.Connector` builds one `DialContext`, so everything above it (bandwidth caps, per-route shaping from 4.3, the connection pool, the audit trail) is unaffected; the same `netguard.CheckHost` call already trusted for a site's own host now also covers a proxy's and a jump's, with no parallel policy to keep in sync; FTP and FTPS get proxy support for free from the same `adapters/proxydial` package SFTP uses.
- Negative: a single jump hop cannot express a multi-hop bastion chain; a target reached through a jump host is only checked by the string configured for it, not by what the jump host's own DNS resolves it to, which is a real (if bounded) trust extension the administrator is making by trusting that jump host at all; keyboard-interactive prompts that are not the stored password (an OTP, a custom challenge) still cannot be answered, matching every other non-interactive SFTP client rather than a genuine limitation introduced here.
