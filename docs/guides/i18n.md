# Internationalization

Sources: [i18next best practices](https://www.i18next.com/principles/best-practices), [MDN Intl](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl).

## Rules

- Every user-facing string goes through i18next; no literals in components.
- Keys are semantic and hold whole sentences; never build sentences by concatenation.
- Interpolate only runtime values; use plural and context features for counts and gender.
- One namespace per feature; languages load lazily.
- Use the typed selector API `t(($) => $.app.name)`; it needs `enableSelector: true` in `CustomTypeOptions`, with resources typed from the English source.
- Create an isolated instance per test with `createI18n(language)`; never share global i18n state.
- English is the source language; add a language by adding `locales/<lang>/<namespace>.json`.
- Format numbers, dates, lists, relative times and byte sizes with `Intl`, never by hand.
- Sort names with `Intl.Collator` (numeric).
- Layout uses logical properties (`ms-*`, `me-*`, `text-start`) and `dir` follows the language.
- The API returns error `code` and `params`; only the client renders text.
- Server-originated text is rendered per recipient locale with `golang.org/x/text`; logs stay English.

## Tests

- CI fails on missing, unused or mismatched keys across locales.
- A pseudo-locale and an RTL run catch hard-coded text and layout bugs.
- Visual baselines exist per language.
