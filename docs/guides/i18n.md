# Internationalization

Sources: [i18next best practices](https://www.i18next.com/principles/best-practices), [MDN Intl](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl).

## Rules

- Every user-facing string goes through i18next; no literals in components.
- Keys are semantic and hold whole sentences; never build sentences by concatenation.
- Interpolate only runtime values; use plural and context features for counts and gender.
- One namespace per feature. Every language is bundled with the app; the files are small and switching needs no request.
- Use the typed selector API `t(($) => $.app.name)`; it needs `enableSelector: true` in `CustomTypeOptions`, with resources typed from the English source.
- Create an isolated instance per test with `createI18n(language)`; never share global i18n state.
- English is the source language; the languages are registered in `frontend/src/i18n/languages.ts` (see [Adding a language](#adding-a-language)).
- Format numbers, dates, lists, relative times and byte sizes with `Intl`, never by hand.
- Sort names with `Intl.Collator` (numeric).
- Layout uses logical properties (`ms-*`, `me-*`, `text-start`) and `dir` follows the language.
- The API returns error `code` and `params`; only the client renders text.
- Server-originated text is rendered per recipient locale with `golang.org/x/text`; logs stay English.

## Tests

- CI fails on missing, unused or mismatched keys across locales.
- A pseudo-locale and an RTL run catch hard-coded text and layout bugs.
- Visual baselines exist per language.

## Adding a language

Anyone can add a language; no code other than one line changes.

1. Copy `frontend/src/i18n/locales/en` to `frontend/src/i18n/locales/<code>`, where `<code>` is the language's [BCP 47 tag](https://www.rfc-editor.org/info/bcp47), such as `fr`, `pt-BR` or `ar`. The folder is picked up by itself.
2. Translate the values of every file. Keep the keys, the nesting and every `{{placeholder}}` exactly as they are.
3. Add the language to `frontend/src/i18n/languages.ts`, with its name written in itself, such as `{ code: 'fr', name: 'Français' }`. That is the name the language menu of Settings shows.
4. Run the translation tests: `docker compose -f compose.dev.yaml run --rm tools sh -c 'cd frontend && pnpm exec vitest run src/i18n'`. They fail on a folder that is not registered, a registered language without a folder, a missing or extra key, an empty message and a placeholder that differs from English, and name each one.
5. Open Settings, choose the language and look at the screens you translated.

Guidelines for translators:

- Translate meaning, not words; keep the tone short and direct, as the English is.
- Leave untranslated: Sentinel, protocol and product names (SFTP, FTP, FTPS, OpenSSH, PuTTY, FileZilla), key and file formats, the stable error codes shown after "Code:", and keyboard shortcuts.
- A message with a count is one sentence with `{{count}}`; do not split it into pieces.
- Right-to-left languages need nothing else: the layout uses logical properties and the page direction follows the language.
- The server only accepts the tag as the account's language and never shows translated text itself, so the backend needs no change.
